## 关键技术点（踩过的坑）
1. **任务栈必须放 PSRAM**：`xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)`。WakeNet 占满内部 RAM 后 `xTaskCreate` 会**静默失败**（任务根本不存在）
2. **TLS 内存**：`CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` + `CONFIG_MBEDTLS_DYNAMIC_FREE_CONFIG_DATA=y`
3. **必须先 SNTP 同步时间**，否则 TLS 证书校验失败（`mbedtls_ssl_setup -0x008D`）
4. **chat_start 前必须 `esp_mcp_create()`** 并传入 config
5. **传输用 WebSocket**：MQTT 会被服务器 EOF 断开
6. **分区表**（C++ 风格）：
   ```
   nvs 0x9000/0x4000, otadata 0xd000/0x2000, phy_init 0xf000/0x1000,
   model 0x10000/0xF0000（esp-sr 自动打包烧录 srmodels.bin）,
   ota_0 0x100000/0x300000, ota_1 0x400000/0x300000,
   assets 0x700000/0x900000（字库等资源，还没用）
   ```
7. **唤醒架构照 C++**：mic 任务只 `feed`，独立 `wake_fetch` 任务阻塞 `fetch_with_delay(portMAX_DELAY)`

# 2026-11-01 下午第二轮修正（用户反馈后）

## 1. 时间快 8 小时（根因 + 修复）
- 现象：本地时间显示 22:0x，实际 14:0x，**快了 8 小时**
- 根因：`components/esp_xiaozhi/src/esp_xiaozhi_info.c` 在解析服务器 `server_time` 时，
  把 `timezone_offset`（分钟）**又加到了 UTC 时间戳上**再 `settimeofday()`：
  ```c
  ts += timezone_offset->valueint * 60 * 1000;   /* ← 错：localtime 自己会加时区 */
  tv.tv_sec = ts / 1000;
  settimeofday(&tv, NULL);
  ```
  系统时钟变成 UTC+8，`display.c` 再 `localtime()`（TZ=CST-8）又加一次 → 显示 UTC+16
- 修复：**关掉这个组件自带的校时**，时间统一交给 SNTP（ntp.aliyun.com）
  - `sdkconfig` / `sdkconfig.defaults` 里：`# CONFIG_XIAOZHI_SYNC_SYSTEM_TIME_FROM_SERVER is not set`
- 验证日志：
  ```
  I display: 时钟: 本地 14:20  UTC 06:20     ← 正确
  ```

## 追加（同日 4）：天气居中 + 圆光环改 2.5D 轨道
### 天气行改成 flex 自动居中
- 问题：原来图标/温度/城市天气是**各自绝对坐标**写死的，Montserrat 24 的温度实际宽度比估的大 →

## 追加（同日 8）：拍照全链路打通 + 三个重启 bug 修复

### 现状（已验证）
唤醒 → 说"拍张照" → MCP 工具 `self.camera.take_photo` → OV3660 拍照（RGB565 QVGA）→
片上 JPEG 编码 → 上传服务器识图 → 返回文字 → 小智念出来 → **聊天框里插入一条图片消息气泡（200×150）**。
连续拍照正常，无崩溃；内部 RAM 约 25~26KB，PSRAM 剩余约 6.8MB。

### 修掉的三个重启原因
1. **MCP 回调栈溢出**：拍照初始化/JPEG 编码/TLS 上传原来都在对话任务的回调里跑（栈只有几 KB）。
   → 拍照全流程挪到独立的 `camera` 任务（**24KB PSRAM 栈**），MCP 回调只发请求+等结果。
2. **LVGL 线程不安全**：`display_show_camera_frame()` 会在摄像头任务里创建/删除 LVGL 对象 → 崩溃。
   → 摄像头任务只做像素缩放/字节序处理并置 `s_photo_pending`，真正的气泡更新放到 LVGL 任务的
   `photo_bubble_update()` 里执行。
3. **图片气泡野指针**：旧气泡可能已被"消息上限"淘汰，仍按裸指针 `lv_obj_delete` → `LoadProhibited`。
   → 改为给气泡 `lv_obj_set_user_data(bubble, PHOTO_BUBBLE_TAG)`，遍历子对象按 tag 删除。

### 其它细节
- 摄像头 RGB565 字节序与 LVGL 相反 → 显示前 `lv_draw_sw_rgb565_swap()`
- 服务器返回的是 JSON（`{"success":true,...,"text":"..."}`）→ 提取 `text` 再返回给大模型，回答更自然
- 像素缩小用最近邻（320×240 → 200×150），不依赖 LVGL 图片缩放

### 已知待优化
- 空闲屏 LVGL 渲染+刷屏仍有 15~20ms/帧（约 15~25fps），下一步可把脸/魔方画布从 ARGB8888
  换成 **RGB565A8**，或把星系背景烘焙进不透明画布，省掉 alpha 混合
- 摄像头逆光/对焦一般（OV3660 自动曝光），可后续调 sensor 参数

## 追加（同日 11）：性能深挖 + 花屏/重启排查结论

### 刷屏性能：每次刷屏固定开销 ~1.8ms
- 实测 **SPI 传输只占 2~3ms/帧**，但每帧要刷 **10 次**（每次 ~1.8ms 固定开销）→ 白烧 18ms
- 每次刷屏 = 一个"不连续的无效区域"；动画对象越多、区域越分散，刷屏次数越多
- 主要元凶：**WiFi 信号格每帧给 4~8 个对象设透明度**、**星星每 3 帧改 8 个对象透明度**
  → 改成"值变了才更新 + 降低频率"后，每帧刷屏 10.5 次 → **5.7 次**，渲染 32ms → **24ms**
- 显示缓冲：**必须双缓冲**（单缓冲时 DMA 还在读，LVGL 已重画 → 花屏）；现为 2×12 行
- LVGL 任务栈必须内部 RAM；LVGL 绘制缓冲必须内部 DMA RAM；LVGL 用 CLIB malloc 释放 64KB 静态池

### 内存结论（无泄漏）
- PSRAM 空闲稳定（6963KB，最低 6926KB）→ **没有 PSRAM 泄漏**
- 内部 RAM 空闲 28KB，但**最低只有 6KB**（启动阶段 esp-sr 模型 + 显示 + 网页服务叠加）
  → 这是花屏/偶发重启的根源；下一步可把"音乐网页服务"改成首次播放时才启动（省 6KB 内部栈）

### 语音控制音乐（已加）
- `self.music.volume`（level 0~100）、`self.music.volume_up`、`self.music.volume_down`
- `self.music.stop` 会同时**取消"对话结束自动续播"**（用户明确要停就不再自动放）
- 音乐播放期间只接受唤醒词，其它对话事件忽略；回音乐界面时主动结束本轮对话通道
